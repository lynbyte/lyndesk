# Phantom WSS video over constrained links — 2026-11-09

What changed (protocol v10): ack-based flow control with a frame window and
a 2×BDP byte budget, delay-based rate control (`crates/server/src/flow.rs`),
OpenH264 bitrate changes without an IDR, scene-change detection and frame
skip off, a QP floor of 24, no periodic keyframes for acking clients. See
`docs/architecture.md` → "Ack-based flow control".

## Method

`crates/server/examples/wan_bench.rs`, the method of voxl's `bench/`:

- Real `run_session_cpu`, real OpenH264 encoder, real WSS send path
  (`transport::ws::raw_ws_session`: same bounded queue + I/O loop as HTTPS,
  no TLS).
- Synthetic 1920x1080 screen at a 60 Hz source rate, with the draw time of
  each frame encoded as a 32-bit marker. Server at phantom's defaults:
  30 fps, 5000 kbps start.
- Userspace bottleneck link: rate limit, RTT split per direction, FIFO queue
  of 500 ms of link time (deep but finite; TCP backpressure beyond it).
- Client decodes every frame with OpenH264 and reads the marker. Latency is
  draw → decoded; FPS counts unique frames; PSNR is the luma of every 5th
  decoded frame against the exact source.
- Workloads: `scroll` (text page, 12 px per frame; every ~4.5 s it wraps to
  the top, a full-screen content change), `anim` (full-screen animation),
  `window` (static desktop + 960x540 animated window).
- 20 s per run after 3 s warmup, one run per cell (scroll at 20 and 10 Mbps
  repeated 3x, below).
- Machine: Intel i5-1135G7 (4C/8T), 16 GB, Windows 11; server, link and
  client on one host. Audio capture (WASAPI) was on, as in production.
- `WAN_BENCH_TRACE=<ms>` logs each frame slower than that, with UTC time, to
  line up with `RUST_LOG=phantom_server::session=debug` rate decisions.

Variants:

- **0.5.10** — git `7757e9d` plus only the bench helper.
- **new** — this change, client acking (current web WSS + native client).
  Clients that never ack keep the old ping ABR and 2 s keyframes; with
  only the encoder fixes they were within noise of 0.5.10 except scroll
  (no dropped frames, 10 instead of 30 keyframes).

Reproduce:

```
cargo run --release -p phantom-server --no-default-features --features audio \
    --example wan_bench -- --secs 20 --profiles lan,20/20,10/40,5/60,2/100
```

## Reading it

- **Latency**: better or equal in every cell. The constrained links are
  where it matters: at 2 Mbps/100 ms 0.5.10 queues 1.4–2.7 s of video, the
  new path 100–300 ms; at 5 Mbps window p95 216 → 74 ms. Scroll p99 at
  20 Mbps is a tie across runs (104–114 vs 107–122).
- **Smoothness**: equal or more frames everywhere, worst seconds included
  (2 Mbps window 9 → 29 fps).
- **No unrequested keyframes**: 0 instead of 10–31 per 20 s (OpenH264 scene
  detection fired every ~0.6 s while scrolling; frame skip dropped a third
  of the scroll frames).
- **Bandwidth**: the window workload needs 1.24 instead of 3.5 Mbps.
- **Quality trade-offs, honestly**: scroll is sharper (+1.7 to +7 dB
  except at 2 Mbps); animation and the video window are 0.5–0.8 dB lower,
  because the QP floor of 24 stops OpenH264 from spending bits below it.
  The floor is what keeps a full-screen change from becoming a ~400 KB
  frame (scroll p99 at 20 Mbps was 216 ms without it). At 2 Mbps animation
  gives up 3.5 dB for +7 fps and ~1 s less latency.
- **How the tail was found**: `WAN_BENCH_TRACE` showed each p99 spike was
  one full-screen change — a 393 KB P-frame (26× budget) plus four frames
  queued behind it. The byte budget removed the queueing; the QP floor
  shrank the frame. x264 with a 1.25-frame VBV (optional `x264` feature,
  not yet benchmarked) would bound it without the floor.
- **Not covered**: packet loss (the link is lossless, as in voxl's runs),
  60 fps server config, GPU encoders (NVENC VBV change untested on
  hardware here), WebRTC, Windows service mode (no flow window there), a
  real browser, and a head-to-head with voxl on the same machine.

## Capture (same machine)

`crates/server/examples/capture_bench.rs`, 1920x1080:

| Backend          | Grab p50 | Note                                              |
|------------------|----------|---------------------------------------------------|
| scrap (DXGI)     | 4.5 ms   | only after the server stopped initialising CUDA   |
| GDI              | 16.3 ms  | what `auto` fell back to                           |
| scrap after CUDA | fails    | `connection refused` (DXGI_ERROR_UNSUPPORTED)      |

On this hybrid-GPU laptop (Intel Iris Xe + GeForce MX350) the GPU probe's
CUDA init bound the process to the discrete GPU, and Desktop Duplication of
the Intel-driven display failed, so `auto` exited and `--capture scrap`
never worked. The server now skips the probe for CPU encoders
(`--encoder openh264`), and `auto` falls back scrap → GDI and NVENC →
OpenH264 instead of exiting.
